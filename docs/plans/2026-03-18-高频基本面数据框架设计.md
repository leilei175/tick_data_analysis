# 高频基本面数据下载与管理框架设计

## 1. 目标

基于 [`docs/plans/2026-03-18-高频基本面数据需求.md`](/data1/code_git/tick_data_analysis/docs/plans/2026-03-18-高频基本面数据需求.md) 中列出的高频宏观、利率、产业和另类数据，设计一套适合当前仓库的数据下载、存储、治理和因子供给框架。

本设计只定义框架，不涉及具体代码实现。

## 2. 设计原则

1. 按“数据源能力”而不是按“因子名称”组织下载链路。
2. 原始数据、标准化数据、因子特征分层存储，避免相互覆盖。
3. 标准接口类数据走全自动增量更新，网页抓取类数据走半自动可恢复任务，付费终端类数据走统一适配器。
4. 所有数据集必须具备元数据注册、版本记录、质量检查和可回溯能力。
5. 目录结构尽量复用现有 `daily_data/`、`factor/`、`doc/` 体系。

## 3. 数据分层

建议新增一套面向高频基本面数据的三层结构。

### 3.1 Raw 层

用途：保留最原始响应，便于追查口径变化、页面改版和字段漂移。

- API 类：保存原始 JSON / CSV / 响应快照
- 网页类：保存 HTML、解析前表格、公告 PDF、公众号文本
- 商业终端类：保存原始导出表或 SDK 直接落盘结果

建议目录：

```text
daily_data/hf_raw/
  macro/
  rates/
  industry/
  inflation/
  futures/
```

### 3.2 Standard 层

用途：将不同来源的数据统一成项目内部标准表结构，作为研究和特征生产的唯一输入层。

建议目录：

```text
daily_data/hf_standard/
  dataset=<dataset_name>/
    freq=<tick|1m|hour|day|week>/
      year=YYYY/
        month=MM/
```

存储格式建议统一为 `parquet`。

### 3.3 Feature 层

用途：存放直接供模型使用的派生指标，如环比、同比、期限利差、滚动 z-score、偏离度、周频映射后的日频特征等。

建议目录：

```text
factor/fundamental_high_frequency/
  raw_features/
  aligned_features/
  merged_panels/
```

## 4. 数据域划分

按需求文档，建议将数据注册为 5 个域。

### 4.1 `macro_liquidity`

- DR007
- OMO 逆回购利率
- OMO 净投放量
- MLF 利率
- 1Y AAA NCD 收益率
- 票据转贴现利率

特点：频率高、时间敏感、适合以交易日为主索引。

### 4.2 `rates_curve`

- 中债收益率曲线关键期限
- 现券隐含收益率曲线

特点：横截面期限维度明显，主键需要包含 `tenor`。

### 4.3 `futures_market`

- 国债期货主力及指定合约行情

特点：Tick / 分钟频率，数据量最大，应与日度产业数据隔离存储。

### 4.4 `growth_proxy`

- 高炉开工率
- 沥青装置开工率
- 沿海八省电煤耗量或替代序列
- 30 大中城市商品房成交面积
- 水泥出库量
- 乘用车周销量

特点：来源分散，口径易变，更依赖元数据和来源版本记录。

### 4.5 `inflation_proxy`

- 农产品批发价格 200 指数
- 猪粮比价
- 南华工业品指数

特点：中低频但更新及时，适合与日度宏观特征直接融合。

## 5. 标准数据模型

为避免每个数据集各自定义结构，Standard 层建议统一采用以下逻辑字段。

### 5.1 通用主键

- `dataset_name`
- `source`
- `symbol` 或 `indicator_code`
- `observation_time`
- `freq`

其中：

- 宏观单指标序列可用固定 `indicator_code`
- 利率曲线需追加 `tenor`
- 期货行情需追加 `contract_code`
- 区域类数据可追加 `region`

### 5.2 通用字段

- `value`
- `unit`
- `currency`
- `publish_time`
- `trade_date`
- `calendar_date`
- `is_revision`
- `revision_no`
- `source_priority`
- `ingest_time`
- `data_version`
- `extra_json`

### 5.3 推荐的两张核心逻辑表

1. 指标时序表 `hf_indicator_series`
   适用：DR007、OMO、NCD、猪粮比、农产品指数、高炉开工率等

2. 行情时序表 `hf_market_series`
   适用：国债期货、收益率曲线、期限结构类数据

## 6. 元数据注册中心

这是整个框架的核心。每个数据集都必须先注册，下载任务才能运行。

建议维护一份注册表，例如：

```text
doc/hf_fundamental_registry.yaml
```

每个数据集至少记录以下信息：

- `dataset_name`
- `domain`
- `source_type`
  - `api`
  - `crawler`
  - `vendor_sdk`
- `provider`
- `upstream_identifier`
- `frequency`
- `update_window`
- `primary_key`
- `time_field`
- `value_field`
- `partition_scheme`
- `retention_policy`
- `sla`
- `expected_delay`
- `quality_rules`
- `fallback_source`
- `license_level`

示例：

- `dr007_cfets`
  - `source_type: api`
  - `frequency: intraday`
  - `primary_key: [indicator_code, observation_time]`
  - `fallback_source: wind_edb_dr007`

- `steel_blast_furnace_rate`
  - `source_type: vendor_sdk`
  - `frequency: weekly`
  - `primary_key: [indicator_code, observation_time]`
  - `license_level: paid`

## 7. 下载框架设计

下载层不要按脚本堆砌，建议按适配器模式设计。

### 7.1 适配器分层

1. `Source Adapter`
   负责和上游交互。
   示例：AkShare、Tushare、Wind/iFinD、网页抓取、公众号解析。

2. `Normalizer`
   将原始字段映射为项目标准字段。

3. `Validator`
   执行字段完整性、时间连续性、重复值、异常跳变校验。

4. `Loader`
   将数据写入 Raw 和 Standard 层，并写入元数据日志。

### 7.2 三类下载路径

#### A. 标准 API 路径

适用：

- DR007
- OMO
- MLF
- 猪粮比
- 南华工业品指数
- 中债收益率曲线历史数据

策略：

- 按交易日或自然日增量拉取
- 支持补历史和重跑最近 N 天
- 失败后自动重试

#### B. 网页抓取路径

适用：

- 票据转贴现利率
- 农产品批发价格 200 指数
- 房地产成交面积
- 乘联会周报文本提取

策略：

- 先落 Raw，再解析入 Standard
- 页面模板变更时只影响解析层，不覆盖原始快照
- 对 PDF / 微信公众号类数据单独保留文本提取产物

#### C. 付费终端路径

适用：

- Wind EDB
- iFinD
- MySteel
- 隆众 / 卓创

策略：

- 外部接口凭证集中管理
- 同一指标允许多源切换，优先使用授权稳定源
- 所有 vendor 数据记录口径版本和下载批次

## 8. 调度与更新策略

不同数据频率差异很大，建议分 4 类调度。

### 8.1 盘中任务

适用：

- DR007
- 国债期货行情
- NCD 收益率

特征：

- 高频或准实时
- 只做增量 append
- 不做重计算，重算交给盘后任务

### 8.2 盘后任务

适用：

- OMO
- MLF
- 南华指数
- 农产品指数

特征：

- 每日固定时间拉取
- 生成日度标准表
- 执行当天质量校验

### 8.3 周频任务

适用：

- 高炉开工率
- 水泥出库量
- 乘用车销量

特征：

- 允许滞后更新
- 必须带“统计周期起止时间”
- 需要映射到交易日特征表

### 8.4 修订回补任务

适用：

- 任何存在补发、修订、口径变更的数据集

特征：

- 每周或每月回刷最近 30-90 天
- 比较新旧版本差异
- 若变动超过阈值，写入修订日志

## 9. 存储与分区建议

### 9.1 Parquet 作为主存储

当前仓库已经广泛使用 `parquet`，高频基本面框架继续沿用即可。

### 9.2 不同数据采用不同分区粒度

- Tick / 分钟数据：按 `dataset/year/month/day` 分区
- 日频数据：按 `dataset/year/month` 分区
- 周频数据：按 `dataset/year` 分区

### 9.3 大体量行情隔离

国债期货 Tick 数据建议单独目录，例如：

```text
daily_data/hf_standard/dataset=govt_futures_tick/
```

不要与宏观单值序列混放，否则后续读取和维护都会变差。

## 10. 数据质量控制

每次下载后都必须执行数据集级校验，至少包含：

1. 主键唯一性检查
2. 时间戳单调性检查
3. 空值率检查
4. 当日值域检查
5. 环比跳变检查
6. 分区行数异常检查
7. 上游发布时间延迟检查

建议把校验结果落到单独目录：

```text
log/hf_data_quality/
```

并为每个批次生成：

- `run_id`
- `dataset_name`
- `status`
- `rows_raw`
- `rows_standard`
- `error_message`
- `warning_message`

## 11. 口径变化与版本管理

需求文档中的产业数据最容易发生“同名指标不同口径”的问题，必须显式管理版本。

建议规则：

1. `dataset_name` 表示业务含义，不表示最终口径版本。
2. 新口径出现时，通过 `data_version` 或 `methodology_version` 区分。
3. 原始口径说明保存在注册表和文档中，不写死在代码里。
4. 特征层只依赖“当前生效版本”，但保留历史版本可回放。

例如：

- `coastal_coal_consumption`
  - `v1`: 沿海八省电煤耗量
  - `v2`: 重点电厂日耗替代口径

## 12. 因子供给层设计

下载和管理框架的目标不是只存原始数据，而是稳定供给因子研究。

建议增加一个“对齐层”：

### 12.1 对齐原则

- 所有低频数据最终都映射到交易日索引
- 周频/月频指标采用“发布后生效”而不是“统计期末生效”
- 盘中数据可同时产出日内特征和收盘聚合特征

### 12.2 对齐后的常见派生特征

- 水平值
- 1 日 / 5 日 / 20 日变化
- 同比 / 环比
- 滚动均值 / 标准差
- z-score
- 分位数
- 与利率或价格的偏离度
- 跨指标价差 / 利差 / 强弱比

### 12.3 输出结果

建议最终输出两类文件：

1. 单指标特征表
   放在 `factor/fundamental_high_frequency/raw_features/`

2. 研究宽表
   放在 `factor/fundamental_high_frequency/merged_panels/`

## 13. 与当前仓库的衔接方式

为了降低改造成本，建议直接在现有工程中新增以下逻辑边界。

### 13.1 目录衔接

- 原始与标准数据进入 `daily_data/`
- 因子结果进入 `factor/`
- 设计文档和注册表进入 `doc/` 或 `docs/plans/`
- 运行日志进入 `log/`

### 13.2 任务衔接

现有 `update_data.py` 主要面向日线和财务数据，不建议直接混入所有高频基本面逻辑。

更合理的方式是：

- 保留 `update_data.py` 作为现有股票日线链路
- 单独建设 `hf_fundamental` 任务入口
- 最终由统一调度器编排多个任务组

### 13.3 读取衔接

后续研究层只读取 Standard 层和 Feature 层，不直接读取 Raw 层。

## 14. 推荐的最小可行落地顺序

不要一开始覆盖全部数据，建议分三期推进。

### 第一期：低难度标准接口

- DR007
- OMO
- MLF
- 猪粮比
- 南华工业品指数
- 中债收益率曲线

目标：

- 跑通注册、下载、标准化、校验、落盘全链路

### 第二期：中等难度网页类

- 农产品批发价格 200 指数
- 票据转贴现利率
- 乘联会周销量

目标：

- 建立 Raw 快照和解析层分离机制

### 第三期：付费终端和产业数据

- 高炉开工率
- 沥青开工率
- 电煤耗量替代指标
- 房地产成交面积
- 水泥出库量

目标：

- 建立多数据源切换和版本治理机制

## 15. 建议的最终框架形态

整体上，推荐把这套体系定义为：

- 一个注册驱动的下载框架
- 一个分层存储的数据湖
- 一个面向交易日对齐的特征供给层

其核心不是“多写几个下载脚本”，而是统一解决以下问题：

- 数据源异构
- 频率不一致
- 口径易变化
- 原始数据不可回溯
- 因子研究难以稳定复现

如果后续进入实现阶段，下一步应先补一份“数据集注册表模板”和“目录/命名规范”，再决定每个数据源的适配器接口。
